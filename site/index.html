How much does the serving stack actually matter?

Naive Hugging Face, TGI, and vLLM, put through the same load test.

This project asks a simple question: if you swap the way you serve an open-weight LLM — a bare transformers.generate() loop vs. Hugging Face's TGI vs. vLLM — how much does it change what users actually experience? To find out, all three stacks were driven with identical Locust load tests across concurrency levels 1–30 (3 trials each, 45 runs total), measuring time-to-first-token, end-to-end latency, and throughput. A second experiment separately profiled KV-cache memory scaling and 4-bit quantization tradeoffs.

Hypothesis going in
vLLM would deliver roughly 5× the throughput of the naive HF baseline, and hold p95 TTFT under 1 second at 30 concurrent requests. The results below test that directly.

Findings vs. Hypothesis

Methodology

Serving stacks under test

  • Naive HF — a plain Hugging Face transformers generate() loop behind a minimal HTTP endpoint, no batching, one request processed at a time.
  • TGI — Hugging Face's Text Generation Inference server, using its /generate_stream streaming endpoint with continuous batching.
  • vLLM — served via its OpenAI-compatible /v1/completions endpoint (streaming), using PagedAttention and continuous batching. Model: Qwen/Qwen2.5-7B-Instruct.

Load generation

Locust drove each stack with a shared load-testing script (shared/locustfile.py), picking a random prompt from an 8-prompt dataset (max_tokens ranging 40–300, average 133.75) per request. Each concurrency level ran with --users N --spawn-rate N for a fixed 1m window, headless, with an 8-request warmup pass before each stack's sweep. Concurrency levels: 1, 5, 10, 20, 30 — 3 trials each, 45 Locust runs total across the three stacks.

Metrics captured

Two Locust request types were recorded per call: TTFT (time to first streamed byte) and TOTAL (full response time). For each stack × concurrency combination, the 3 trials' per-trial median and p95 values were themselves aggregated by taking the median across trials — smoothing single-run noise without discarding the tail-latency signal. Throughput is Locust's measured requests/sec per trial, similarly aggregated; estimated tokens/sec multiplies that by the dataset's average max_tokens as a rough output-length proxy (not a token-exact count).

Memory experiments

Run as a separate experiment (experiment2_memory/), outside the Locust sweeps. KV-cache scaling swept context length (512–4096 tokens) × concurrency (1–20), recording memory before and after generation and flagging OOM. Quantization compared FP16 vs. 4-bit loading of the same model on the same prompt — memory at rest, peak memory, and generation speed — as a single trial per configuration, not averaged across repeated runs.

Known limitation: the formal automated warmup step was added to the sweep script after the vLLM cold-start issue surfaced mid-project. Naive HF and TGI's c1_trial1 runs predate that change and may carry a small residual cold-start effect (partially offset by incidental manual warmup requests made before each sweep). Documented rather than re-run, to preserve project momentum — a more rigorous version would re-run all three stacks under identical formal warmup.
